# Подключение к T-Invest

Платформа работает без T-Invest. Адаптер `app/broker/tinvest_sandbox.py` проверяет будущую интеграцию и торговым ботом
пока не используется. Адрес песочницы зашит, другого нет, поэтому настоящее поручение отсюда отправить нельзя.

## На чём основано

| Источник | Что дал |
|---|---|
| Контракты `sandbox.proto`, `orders.proto`, `marketdata.proto` в репозитории RussianInvestments/investAPI | Методы и поля |
| Документ `limits.md` там же | Лимиты: песочница 200 запросов в минуту, сервис ордеров 100, котировки 600 |
| Статья T-Банка на Хабре о MCP (№ 1086714) | Адреса MCP, песочница, авторизация |
| Прямые вызовы песочницы 31.10.2026 | Адрес REST, форматы, поведение при повторе, состав инструментов MCP |

Портал `developer.tbank.ru` с этой машины не открылся, поэтому его текст не сверялся. Официальной страницы с описанием
инструментов MCP я не нашёл: их список получен запросом `tools/list` к самому серверу.

## Что идёт через какой канал

| Операция | Канал | Почему |
|---|---|---|
| Отправка заявки | Прямой API | В `PostOrder` есть обязательный `order_id` для идемпотентности. В `invest_create_order` такого поля нет: повтор после обрыва в MCP опасен |
| Снятие и состояние заявки | Прямой API | Можно обращаться по своему ключу (`ORDER_ID_TYPE_REQUEST`) и не хранить номер биржи |
| Поток цен и сделок | Прямой gRPC | `MarketDataStream`, `TradesStream`, `OrderStateStream` есть только там. MCP не предназначен для цикла реакции на рынок |
| Позиции, стакан | Прямой API | Торговый бот и так работает с этим каналом |
| Поиск бумаги, новости, сведения о выпуске | MCP | Удобно агенту: инструменты с описанием, задержка неважна |

Итог: торговый контур идёт через прямой API, MCP остаётся источником сведений для агента. Адаптер `McpReader` разрешает только
чтение и отказывает в торговых инструментах до обращения к сети.

## Что проверено на настоящей песочнице

Скрипт `scripts/check_sandbox.py`, ОФЗ 26238, виртуальный счёт:

- счёт, позиции, стакан, статус торгов через прямой REST `.../rest/tinkoff.public.invest.api.contract.v1.*`;
- продажа с исполнением, заявка вне рынка, её снятие;
- повтор с тем же ключом не создал вторую заявку: позиция изменилась на 1. Сервер отвечает ошибкой `30057`, а не прежним
  результатом, поэтому адаптер читает состояние по ключу;
- чтение счёта через MCP.

Что выяснилось: этапы исполнения (`stages`) пусты, при частых заявках приходит `429`, цены приходят как `units` и `nano`.

## Что нужно для настоящего подключения бота

Простое правило «порог и минимальная цена» в боевом контуре ставилось бы нативной стоп-лимит заявкой брокера
(`PostStopOrder`, `STOP_ORDER_TYPE_STOP_LIMIT`, срок `GOOD_TILL_DATE`): она живёт на стороне брокера и не зависит от
того, запущен ли бот. Свой бот нужен для того, чего стоп-заявка не умеет: порог от максимума после покупки, продажа
частями по стакану, объяснение и итог против удержания. Для него нужно:

1. Поток рыночных данных через gRPC вместо опроса.
2. Запуск бота в отдельном потоке: методы адаптера блокирующие.
3. Сервис `OrderStateStream` или опрос для исполнений и снятие заявки по сроку на стороне бота.
4. Обработка лимитов, `429` и потери связи после отправки.
5. Лоты, шаг цены и единицы цены: у облигаций пункты, у акций рубли.
6. Отдельный токен с минимальными правами.

Запуск проверки:

```bash
TINVEST_SANDBOX_TOKEN=... python scripts/check_sandbox.py SU26238RMFS4_TQOB
```

Если T-Банк недоступен из-за VPN, есть `TINVEST_CONNECT_IP`, `TINVEST_BIND_INTERFACE` и `TINVEST_CA_BUNDLE` (сертификат Минцифры).
